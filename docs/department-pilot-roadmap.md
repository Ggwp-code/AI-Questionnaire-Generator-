# Production roadmap for multi-subject exam papers

Multiple faculty members can create subjects, upload digital or scanned books, select topics from those books, and generate individual questions or a full exam. Each paper records its subject, topic allocation, source editions and faculty approvals. The initial deployment can still be shared by one department. The first demonstration uses two instructors and two distinct subjects. Machine learning is an existing fixture. The second subject should have genuinely different material, such as history. New subjects can be added through the UI without editing prompts or deploying another agent. Worker topology, milestones and targets below are proposals.

## Rebuild requirements for configuration and text

Every course-specific value, deployment setting and tunable policy must have an explicit source. Apply this rule across the UI, API, agents, workers, CLI and exporters. The named subjects, model candidates, paper sizes and timings in this roadmap are examples and benchmark inputs. Keep them in fixtures or benchmark profiles wherever they are used for testing.

| Values | Source in the rebuild |
|---|---|
| Faculty, subjects, topics, units, outcomes, books and editions | Faculty-managed subject records and evidence from the selected uploads. Show missing optional metadata as unassigned. Ask for required metadata before generation. Remove guessed values such as the UI's `CO1` fallback. |
| Marks, question counts, formats, section choices and rubric | The selected, versioned paper template and the instructor's request. Carry that blueprint through drafting, review and export. |
| Agent roles and model assignments, prompt templates, OCR languages, retrieval thresholds, concurrency, retries, timeouts and budgets | Validated, versioned configuration shared by the coordinator and workers. Record the effective versions with the job. |
| Service addresses, allowed origins, ports, storage locations and credentials | Deployment settings and a server-side secret store. Report missing required settings by name at startup. Keep secret values out of logs and browser bundles. |

Use plain text without emojis in all project-authored material, including interface labels, status messages, prompts, source comments, scripts, logs, tests and documentation. Enforce the same rule on generated questions, answer keys, rubrics and rendered exports. Validate drafts before saving or streaming them for display. Apply emoji-aware checks that preserve mathematical operators, units, accents and non-Latin scripts. Preserve original uploaded books for accurate source citations.

**Acceptance checks.** Run the same build against two different deployment profiles and a newly created subject with unfamiliar topics. Change the writer model, OCR language, worker limit and marking scheme through their declared sources. Verify the changes take effect, missing values yield actionable feedback, and no sample course data appears. Add a CI scan for emojis in project-authored text and an end-to-end test that sends an emoji-bearing model response through generation and export. Verify that the displayed question and exported answer key are emoji-free and that equations and multilingual text survive intact.

## Subject libraries and book OCR

The current [syllabus](../app/config/syllabus.json) describes AIML, the [Guardian configuration](../config/syllabus.yaml) names a single course, and the suggestions API matches PDF filenames to units. Replace these inputs with a selected subject library. A faculty member creates or joins a subject, uploads books, and sees a proposed chapter/topic outline derived from contents pages, headings and passages. Each proposed topic links to source pages. Faculty can rename, merge or select topics, or request a topic in their own words. A syllabus upload can refine the outline. Books alone are sufficient to start. Preserve the existing AIML configuration as one importable subject.

1. Store the original privately and enqueue ingestion. Identify the book edition by content hash and each extraction by parser version, settings and language. Grant library access explicitly if faculty share a book. Apply that access scope to retrieval, deduplication, caches and citation downloads.
2. Inspect each page for usable native text and image regions. Preserve good native text. For scans, run OCRmyPDF/Tesseract with the book language, rotation detection and deskew as appropriate. For mixed pages, also inspect image regions even if a header already has selectable text. Extract from the complete searchable document so native pages survive indexing. [OCRmyPDF cookbook](https://ocrmypdf.readthedocs.io/en/latest/cookbook.html)
3. Route difficult tables, multicolumn layouts and formulas to a layout-aware parser such as Docling. Store the original page reference and region coordinates with each passage. Show uncertain symbols, units or table cells beside their source crop for correction. Exclude unresolved regions from evidence for an answer. Index usable chapters and show their readiness while other chapters process. [Docling documentation](https://docling-project.github.io/docling/)
4. Cache completed page extraction and embeddings by version. A revised book gets a new index version. Existing papers keep their cited edition. Benchmark a digital chapter, a photographed chapter, a mixed PDF and a table/formula sample against manually checked passages. Include a changed minus sign or exponent as an answer-critical test.

## Cloudflare deployment

Faculty open one HTTPS address for the application. Build React with Vite, publish the compiled frontend with Workers Static Assets, and send API and progress requests to the same origin. Configure the Worker to handle the API route before single-page navigation. Replace the localhost fallback in the [frontend API client](../frontend/services/api.ts) and keep the [Vite proxy](../frontend/vite.config.ts) in the development profile. The hostname, bindings, limits and secrets come from the target environment. [Cloudflare static asset routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)

| Component | Deployment decision |
|---|---|
| API and agents | A gateway Worker routes authenticated requests to FastAPI in a Cloudflare Container. Package LangGraph and the Python model clients in generation containers. Package OCRmyPDF, Tesseract and the required language data in a separately sized ingestion container. Budget for the Workers Paid plan, which Cloudflare requires for Containers. [Cloudflare Containers](https://developers.cloudflare.com/containers/) |
| Uploaded books and exports | Use private R2 buckets. After checking course access, issue a short-lived upload URL for a single server-assigned object. Configure bucket CORS for the faculty origin and verify the uploaded object before scheduling OCR. Authorize access to cited pages, papers and answer keys on download. [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) |
| Background jobs | Use separate Cloudflare Queues for ingestion and generation. Queue messages carry job and stage identifiers. Consumer Workers dispatch bounded page batches or question slots to the appropriate containers and acknowledge after results are durable. Retry by stage ID, checkpoint progress and surface exhausted retries. Size each batch within the consumer duration limit. [Cloudflare Queues limits](https://developers.cloudflare.com/queues/platform/limits/) |
| Durable state and retrieval | Retain the roadmap's managed PostgreSQL database as a separately provisioned service. Use its vector extension for course-scoped passages, alongside job state, checkpoints, revisions and approvals. Python containers connect through a server-side TLS connection pool. Container disk is temporary workspace for extraction and rendering. |

**Rollout.** First provision isolated staging resources and deployment secrets, apply database migrations, then deploy the container images, Worker and frontend with an environment-specific Wrangler configuration. From another device, sign in at the staging hostname, upload a scanned chapter, generate a paper, reconnect during generation and export the approved result. Verify that browser traffic uses HTTPS with no loopback requests, another course cannot open the source or answer key, and a restarted container resumes the job. Repeat the paper-speed benchmark with cold containers and a concurrent OCR upload. Promote the tested revisions to the production hostname after these checks pass, retaining the previous compatible Worker and image revisions for rollback.

## Cloud-hosted agents and heavy workloads

Run the LangGraph coordinator and every agent role in Cloudflare Containers. FastAPI accepts a paper request, persists the job and returns its ID. Cloud consumers advance the job independently of the browser. An instructor can sign out after submission and return from another device to review the draft. [Cloudflare Containers](https://developers.cloudflare.com/containers/)

Give OCR and indexing their own container pool. Split long books into checkpointed page batches and choose CPU and memory settings from measured extraction throughput and peak memory. Give interactive paper jobs a separate pool and dispatch independent question slots concurrently. Configure per-pool capacity, per-faculty concurrency and provider limits for each deployment. Use queue age, available capacity and the remaining job budget to decide when to start additional work.

Keep model calls server-side. The cloud writer and reviewer call the hosted model assigned to their role. For a difficult derivation, send the relevant slot and cited evidence to the configured reasoning model and record the result. If a supported embedding or reranking model benefits from GPU inference, benchmark Cloudflare Workers AI on retrieval quality, latency and cost before enabling it. Model credentials stay in the cloud deployment's secret store. [Cloudflare Workers AI](https://developers.cloudflare.com/workers-ai/)

| Role | Input and output |
|---|---|
| Planner | Receives the instructor's topic and marks allocation plus the available chapter outline. Emits a numbered slot plan. Application code enforces counts and marks. |
| Evidence retrieval | Takes each slot, authorized subject and selected book versions. Returns ranked passages with page and region IDs or an explicit evidence gap. |
| Writer | Takes one slot and its passages. Returns a typed question, answer, marking guide and citations. Independent slots can run concurrently. |
| Reviewer | Receives the draft and cited passages, checks support and subject-appropriate reasoning, and returns pass, targeted revision or faculty review. |
| Paper assembly | Orders completed slots by their original numbers, checks coverage, choices, duplicate questions and marks, and builds the paper and key from approved versions. |

**Staging acceptance.** Start OCR on a long scanned book while faculty generate papers from indexed material. Close the submitting browser, interrupt a generation container, then sign in from another device. Verify that completed slots survive, the unfinished slot resumes, and exactly one reviewable paper appears. Compare time to first reviewed question and total draft time against the paper-speed targets below. Record OCR throughput, queue wait, provider time and cost per accepted question so the team can identify which pool or model needs adjustment.

For example, an instructor requesting *trees* in machine learning should retrieve decision-tree passages. The same request in botany should search only the selected botany books. If those books lack the topic, show the evidence gap. This exercises subject selection, cache isolation and citation correctness with the same user input.

## The workflow to build

1. **Ingest once per document version.** Store the original PDF privately. Record course, checksum, page, passage offsets, chunk ID and extraction version. Validate the PDF and apply size/page limits before processing. Show extraction failures and flag scanned or formula-heavy pages for inspection. Mark a document ready only after its passages can be retrieved.
2. **Turn the template into an exam blueprint.** Expand sections into numbered slots with unit, outcome, question type, marks and intended Bloom level. Validate counts, compulsory and optional choices, and marks before any model call. Show an invalid template to the author immediately.
3. **Retrieve evidence for each slot.** Filter to the selected course and document versions before ranking. Return passage records and their source pages. Keep previous-year papers as references for style and duplication checks. If there is insufficient course evidence, flag the slot and let the author select more material.
4. **Generate a typed draft.** Give the writer the slot and its passages. Require a question, answer, marking rubric and citations, plus type-specific fields such as options and correct option for an MCQ. Treat retrieved text as source material. Record model ID, prompt version, retrieval version and token usage with each attempt.
5. **Verify and revise selectively.** Check required fields, option consistency, mark totals, citation resolution and duplicates in code. Use trusted calculation functions for supported numerical questions. Route unsupported calculations to faculty review. A reviewer model sees the actual evidence, checks whether it supports the answer, and gives specific correction reasons. Allow one targeted revision initially. Exhausted retries, provider errors and disagreements remain visible.
6. **Approve and assemble.** Let instructors open the cited passage, edit, reject, regenerate a single slot or approve it. An edit invalidates the affected checks and approval. Assemble the exam and answer key from the same approved revisions. Check paper-wide duplicates, coverage, question choices and answer-key alignment before export. Record who approved which revision.

### Model routing

Start with one hosted provider behind a small role-based interface. Supply known metadata directly from the template. Use a low-cost model only for genuinely ambiguous classification, a general model for drafting, and a stronger reasoner for difficult derivations or disputed reviews. Keep the current local embedding model as a retrieval baseline. Measure whether a change improves retrieval of the faculty-labelled source pages.

For an initial experiment, compare GPT-6.2 Sol for drafting and GPT-6.2 Astra for escalation against a single strong-model call with the same evidence and output schema. GPT-6 Luna is a candidate for low-cost tagging. If the department permits a second provider, Claude Sonnet 5.5 is another drafting candidate for the offline comparison. Select by faculty ratings, cost per accepted question and latency. Pin the winning configuration, record it per run, and rerun the comparison before changing it. [OpenAI model catalog](https://developers.openai.com/api/docs/models) · [Anthropic model catalog](https://platform.claude.com/docs/en/models/overview)

## Delivery order and acceptance checks

Build the shortest usable path first. The initial milestone needs a digital chapter and a scanned chapter from different subjects, permission to use those samples and faculty who can judge the results. Time-box the first two milestones to a two-week prototype with one engineer, then use measured OCR throughput, model latency and faculty feedback to schedule the production rollout.

## Paper generation speed

Move OCR, chapter detection and embedding to upload time. Accept a paper request against ready chapters, validate its blueprint, and return a job ID immediately. Start with four concurrent slots across a paper, enforce a global provider limit across all workers, and reserve fair capacity across faculty. Stream the first reviewed question while other slots run. If a slot fails, retry that slot by ID. The final paper uses blueprint order even if questions finish out of order. Human approval and final export are tracked separately.

Proposed performance experiment: submit five simultaneous ten-question papers using already indexed chapters, empty question caches and a fixed mix of MCQs and short answers. Target p95 under 30 seconds for the first reviewed question and under two minutes for a complete reviewable draft, including queue wait. Measure cold upload-to-searchable-chapter time and OCR pages per minute separately by scan type and worker hardware. Also run a long OCR job during the paper benchmark. If targets are missed, examine queue time, retrieval, provider calls and retries before raising concurrency. A partial or failed paper counts as a miss.

## How to decide whether the pilot is ready

Use a held-out set of around 100 requests across the pilot subjects, covering native and OCR sources, overlapping topic names, all supported question formats, easy and difficult items, and deliberate missing-source cases. Have faculty identify acceptable source pages and grading criteria. Blind the output labels and vary presentation order. Keep previous-year questions used for grading out of generation context and the question cache for those runs.

| Proposed pilot gate | Measurement |
|---|---|
| Faculty accept at least 85% of answerable drafts with at most minor wording edits | Report results by subject, source type and question type alongside the legacy and direct-model baselines. Count a wrong key or a substantive rewrite as a failure. A second reviewer adjudicates disputed scores. |
| Every export passes structural and approval checks | No blank fields, placeholder questions, unapproved revisions or incorrect mark totals. All citations open the correct document version and page. Faculty separately judge whether the passage supports the answer. |
| No critical answer-key error in the release sample | Include numerical and multi-part cases. Record the sample size. An unsupported or disputed answer stays in review until resolved. |
| Cost and wait time fit department limits | Track provider spend including retries and failed jobs divided by faculty-accepted questions. Report median and p95 time per question and per representative full paper, including queue time. Validate the proposed latency targets under the stated load and agree on a spending ceiling with participating faculty after the first measured run. |
| Recovery works in staging | With concurrent faculty requests, interrupt one worker mid-paper, reconnect a browser and repeat a submission. Verify a single final artifact, intact approvals, and no cross-course access. Drill restoration from backup before launch. |

Start the live pilot with multiple faculty across at least two subjects and draft-only access. Enable faculty-approved exports once the gates pass. Monitor queue age, rejection reasons, provider errors, token spend and edit rates by model and prompt version. Keep traces free of paper text by default. Pause new jobs or revert the model configuration if costs or errors spike. Preserve already-approved papers and their audit history.

**First implementation ticket.** Give two faculty accounts separate subject libraries. Upload a digital chapter to one and a scanned chapter to the other. Let each instructor select a source-backed topic and generate a three-question paper with an answer key and clickable page citations. Acceptance:

- Both instructors first receive three supported questions. Then one instructor requests, as a separate request, a topic covered only in the other instructor's book. The outcome is an explicit evidence gap, with no generated answer and no citation from that book. Direct requests for the other instructor's PDF, cited passage, paper and answer key are refused.
- Prove the scanned-book path with real OCR. CI keeps the simulated OCR test. For acceptance, upload a scan with no usable text layer, run the deployed OCR engine and the configured model, and have a reviewer open each cited page and confirm that it supports the answer. A citation can point to the right page and still support the wrong answer, especially if OCR misreads a symbol.
- Faculty return later. Regenerate one slot the next day: the other two keep their revision IDs, citations and approvals, and the replacement requires fresh approval. Reprocess the identical book and confirm that the previously approved key still exports.
- Timers start when the server accepts a paper request against an indexed chapter, so queue time is included. Record when the first reviewed question is available to the instructor and when all three slots have a visible outcome. Measure upload-to-searchable time separately, so slow OCR and slow generation can be diagnosed independently.
